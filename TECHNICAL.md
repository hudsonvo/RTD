## 2. Frontend Architecture

**Single-page application** built with React 19 + Vite 8. No server-side rendering.

### Module system
The project uses ES modules (`"type": "module"` in package.json). Every file uses `import`/`export` — no CommonJS `require()`.

### Rendering approach
Standard React functional components with hooks. No class components. No Redux or Zustand — all state is either:
- Component-local `useState`
- Shared via React Context (`AuthContext`)
- Derived at render time from props

### Styling
Tailwind CSS v4, loaded via the `@tailwindcss/vite` Vite plugin (not PostCSS). This means no `tailwind.config.js` — Tailwind scans source files automatically. Global base styles in `src/index.css`.

### Routing
React Router v7 with `BrowserRouter`. All routes are defined in `src/App.jsx`. The `/account` route is wrapped in `ProtectedRoute` which checks `AuthContext.user` and redirects to `/login` if null.

```jsx
// ProtectedRoute pattern
if (loading) return <LoadingSpinner />
if (!user) return <Navigate to="/login" state={{ from: location.pathname }} replace />
return children
```

The `state={{ from: location.pathname }}` allows Login to redirect back to the originally requested page after authentication.

## 4. GTFS-Realtime: Raw Format & Pipeline

### What GTFS-RT is
GTFS-Realtime is a Google-designed binary protocol for distributing live transit data. The binary format is **Protocol Buffers** (protobuf), defined by a `.proto` schema that Google publishes. RTD exposes three feeds.

### Raw binary decoding
```js
import { transit_realtime } from 'gtfs-realtime-bindings'

const res = await fetch('/api/gtfs-rt/rtd/VehiclePosition.pb')
const buffer = await res.arrayBuffer()
const feed = transit_realtime.FeedMessage.decode(new Uint8Array(buffer))
```

`gtfs-realtime-bindings` is a pre-compiled JS library that knows the protobuf schema. It returns a `FeedMessage` object with this structure:

```
FeedMessage
  .entity[]                   array of FeedEntity
    .id                       string identifier
    .vehicle (VehiclePosition feed)
      .trip.routeId           e.g. "15"
      .trip.tripId            e.g. "5476284-SEP24-MVS-Weekday-01"
      .trip.directionId       0 or 1
      .position.latitude      float
      .position.longitude     float
      .position.bearing       degrees (0 = North, 90 = East)
      .position.speed         metres per second
      .vehicle.label          human-readable vehicle number
      .stopId                 next stop
    .tripUpdate (TripUpdate feed)
      .trip.routeId
      .trip.tripId
      .stopTimeUpdate[]
        .stopId               which stop
        .arrival.time         unix timestamp (Long)
        .arrival.delay        seconds (positive = late)
        .departure.time
        .departure.delay
    .alert (Alerts feed)
      .informedEntity[]
        .routeId
      .activePeriod[]
        .start                unix timestamp
      .effect                 integer enum (1=NO_SERVICE, 3=SIGNIFICANT_DELAYS, etc.)
      .headerText.translation[].text
      .descriptionText.translation[].text
```

### Transformation: VehiclePosition feed → app vehicle objects

`fetchVehiclePositions()` in `rtdFeeds.js`:
```
Raw protobuf entity → {
  id:           e.id,
  routeId:      v.trip?.routeId ?? '',
  tripId:       v.trip?.tripId ?? '',
  lat:          v.position.latitude,
  lon:          v.position.longitude,
  heading:      v.position.bearing ?? 0,
  speed:        Math.round((v.position.speed ?? 0) * 2.237),  // m/s → mph conversion
  vehicleLabel: v.vehicle?.label ?? e.id,
  nextStop:     v.stopId ?? null,
  directionId:  v.trip?.directionId ?? 0,
  delay:        0,  // filled in later by merging TripUpdates
}
```

### Transformation: TripUpdate feed → delay map

`fetchTripDelays()` returns a plain object keyed by `tripId`:
```
{ [tripId]: { delay: minutes, etaSec: unix_timestamp_or_null } }
```

The `delay` is taken from the first `stopTimeUpdate` entry (the most imminent stop). The raw value is in **seconds**, converted to **minutes** with `Math.round(delaySec / 60)`.

`etaSec` is a protobuf `Long` type (because JS can't safely handle 64-bit integers), so it's cast with `Number(etaRaw)` before use.

### Merging in `useVehiclePositions()`

```js
const [positions, delays, stops, directions] = await Promise.all([
  fetchVehiclePositions(),
  fetchTripDelays(),
  getStops(),
  getDirections(),
])
positions.map(v => ({
  ...v,
  delay:        delays[v.tripId]?.delay ?? 0,
  etaSec:       delays[v.tripId]?.etaSec ?? null,
  nextStopName: resolveStopName(stops, v.nextStop),
  headsign:     resolveHeadsign(directions, v.routeId, v.directionId),
}))
```

All four calls run in parallel with `Promise.all`. The stop name and headsign lookups use the static GTFS JSON files (described next).

### Arrivals at a stop

`fetchArrivalsAtStop(stopId)` iterates every `stopTimeUpdate` in every `tripUpdate` entity looking for entries where `stu.stopId === stopId`. It filters out times in the past (`etaSec < nowSec`) and returns the closest 12 upcoming arrivals sorted by ETA.

### Alert severity mapping
RTD's GTFS-RT uses the integer `effect` field. The app maps:
```js
effect 1 (NO_SERVICE) or 3 (SIGNIFICANT_DELAYS) → 'warning'
effect 5 (ADDITIONAL_SERVICE) or 6 (MODIFIED_SERVICE) → 'success'
all others → 'info'
```

Translated text is extracted by finding the English translation first, falling back to the first available language.

## 5. GTFS Static: Raw Format & Pipeline

### Source
RTD publishes a `.zip` file containing CSV files following the [GTFS static spec](https://gtfs.org/schedule/reference/). Relevant files inside the ZIP:

| CSV file | Key columns used |
|---|---|
| `stops.txt` | `stop_id`, `stop_name`, `stop_lat`, `stop_lon` |
| `trips.txt` | `route_id`, `trip_id`, `direction_id`, `trip_headsign`, `shape_id` |
| `shapes.txt` | `shape_id`, `shape_pt_lat`, `shape_pt_lon`, `shape_pt_sequence` |

### Build-time processing (`scripts/fetch-gtfs-static.js`)

Run once via `npm run update-gtfs`. Downloads the ZIP, extracts the CSVs, and writes three JSON files to `public/`:

**`gtfs-stops.json`** — flat object, keyed by `stop_id`:
```json
{
  "1234": { "name": "Colfax & Broadway", "lat": 39.7403, "lon": -104.9882 },
  "5678": { "name": "Union Station", "lat": 39.7530, "lon": -105.0002 }
}
```

**`gtfs-directions.json`** — keyed by `"routeId:directionId"`:
```json
{
  "15:0": "Downtown Denver",
  "15:1": "East Colfax"
}
```

**`gtfs-shapes.json`** — keyed by `shape_id`, value is coordinate array:
```json
{
  "p_1234567": [[39.748, -104.998], [39.750, -104.996], ...]
}
```
Shapes are grouped by `shape_id` and sorted by `shape_pt_sequence`.

### Runtime usage (`src/api/gtfsStatic.js`)

All three files are fetched with `fetch('/gtfs-stops.json')` etc. Each has an in-memory cache variable (`stopsCache`, `directionsCache`, `shapesCache`) — once loaded for a session, they are never re-fetched.

Key utility functions:
- `resolveStopName(stops, stopId)` — O(1) object lookup
- `resolveHeadsign(directions, routeId, directionId)` — looks up `"routeId:directionId"`, falls back to `"routeId:0"`
- `findNearbyStops(stops, lat, lon, maxMeters, maxResults)` — iterates all stops, computes haversine distance, filters and sorts
- `searchStops(stops, query)` — `String.toLowerCase().includes()` substring match over all stop names

## 6. OpenTripPlanner: GraphQL API & Data Pipeline

### What OTP is
OpenTripPlanner is an open-source Java application that builds a routing graph from GTFS data and exposes a GraphQL API. It runs locally on port 8080. The routing engine knows about every stop, trip, schedule, and transfer in RTD's network.

### GraphQL query structure

OTP 2.6 uses GraphQL (not REST). All queries go to `POST /otp/gtfs/v1` with a JSON body:
```json
{ "query": "...", "variables": { ... } }
```

The query is built dynamically based on whether a datetime or transport modes are needed:
```js
function buildPlanQuery(includeDateTime, includeModes) {
  const dtVar    = includeDateTime ? ', $dateTime: Long' : ''
  const modesVar = includeModes    ? ', $transportModes: [TransportMode]' : ''
  // ... constructs a GraphQL query string
}
```

The `dateTime` variable is type `Long` in OTP (64-bit epoch milliseconds) — this is why the datetime input is converted with `new Date(datetime).getTime()`.

### Transport mode arrays

```js
const TRANSIT_MODES = [
  { mode: 'WALK' }, { mode: 'BUS' }, { mode: 'TRAM' },
  { mode: 'RAIL' }, { mode: 'SUBWAY' }, { mode: 'FERRY' },
]
const DRIVE_ONLY_MODES = [{ mode: 'CAR' }]
```

These are passed as `transportModes` variables in the GraphQL request. OTP uses them to restrict which travel modes it considers.

### Raw OTP itinerary response shape

```json
{
  "data": {
    "plan": {
      "itineraries": [
        {
          "duration": 3840,
          "startTime": 1750000000000,
          "endTime":   1750003840000,
          "legs": [
            {
              "mode": "WALK",
              "duration": 300,
              "distance": 250.4,
              "from": { "name": "Origin", "lat": 39.74, "lon": -104.98 },
              "to":   { "name": "Union Station", "lat": 39.75, "lon": -105.00 },
              "route": null,
              "legGeometry": { "points": "y`olFhkqpSsA@..." },
              "intermediateStops": []
            },
            {
              "mode": "RAIL",
              "duration": 2400,
              "from": { "name": "Union Station", ... },
              "to":   { "name": "DIA", ... },
              "route": { "shortName": "A", "longName": "University of Colorado A Line", "color": "005DAA" },
              "legGeometry": { "points": "encoded_polyline_string" },
              "intermediateStops": [{ "name": "40th & Airport" }, ...]
            }
          ]
        }
      ]
    }
  }
}
```

### Google Polyline Algorithm decoding

`legGeometry.points` is a string encoded with the [Google Polyline Algorithm](https://developers.google.com/maps/documentation/utilities/polylinealgorithm). This is a compact ASCII encoding of a coordinate array.

The `decodePolyline(encoded)` function in `otp.js` implements the decode algorithm:
1. Iterate characters, reading variable-length chunks
2. Each chunk encodes a signed integer delta (difference from previous coordinate)
3. Divide by `1e5` to get decimal degrees
4. Accumulate lat and lon separately

Result: `[[lat, lon], [lat, lon], ...]` — directly usable as Leaflet `Polyline` positions.

### `formatItinerary()` — normalizing OTP output

Converts one raw OTP itinerary into a consistent app format:

```js
{
  id: 0,
  duration: "64 min",
  departure: "5:09 PM",
  arrival:   "6:13 PM",
  legs: [
    {
      type: "walk",
      desc: "Walk to Union Station",
      time: "5 min",
      geometry: [[lat,lon], ...],   // decoded polyline
      fromCoords: [39.74, -104.98],
      toCoords:   [39.75, -105.00],
    },
    {
      type: "transit",
      routeId: "A",
      routeColor: "#005DAA",        // prepended '#' to OTP's hex string
      routeType: "light-rail",      // mapped from OTP mode enum
      desc: "A toward DIA",
      stops: 3,
      time: "40 min",
      geometry: [[lat,lon], ...],
      fromCoords, toCoords,
      fromName: "Union Station",
      toName: "Denver International Airport",
    }
  ]
}
```

OTP returns `color` without the `#` prefix — the formatter prepends it: `` `#${leg.route.color}` ``.

OTP mode strings map to app types:
```js
{ BUS: 'bus', TRAM: 'light-rail', RAIL: 'commuter-rail', SUBWAY: 'light-rail' }
```

### Drive+Transit: two-call merge (`planCombinedDriveTransit`)

```js
const [driveItins, transitItins] = await Promise.all([
  planTrip({ ..., transportModes: DRIVE_ONLY_MODES }),   // origin → P&R
  planTrip({ ..., transportModes: TRANSIT_MODES }),       // P&R → destination
])
```

Both calls run in parallel. The first item from each response is taken (`itins[0]`), formatted, and the leg arrays are concatenated:

```js
legs: [...driveF.legs, ...transitF.legs]
```

Total duration is `driveItins[0].duration + transitItins[0].duration` (both in seconds, converted to minutes). The display times are derived from `startTime` of the drive leg and a calculated arrival using the summed duration.

## 7. Nominatim: Geocoding API

Nominatim is OpenStreetMap's geocoding service. It accepts a free-text address and returns coordinates.

### Request
```
GET /search?q=Union+Station+Denver&format=json&limit=6
  &countrycodes=us
  &viewbox=-105.5,39.4,-104.4,40.2
  &bounded=0
```

`viewbox` biases results toward the Denver metro bounding box. `bounded=0` means results outside the box are still returned if nothing local matches (soft bias).

### Raw response (array of objects)
```json
[
  {
    "place_id": 123456,
    "display_name": "Union Station, 17th Street, LoDo, Denver, Denver County, Colorado, 80202, United States",
    "lat": "39.753002",
    "lon": "-105.000305",
    "type": "station",
    ...
  }
]
```

`lat`/`lon` come back as **strings** — parsed with `parseFloat()`.

`display_name` is the full comma-separated address. The app trims it to 3 components:
```js
r.display_name.split(',').slice(0, 3).join(', ').trim()
// → "Union Station, 17th Street, LoDo"
```

### Debouncing

The `AddressInput` component debounces the geocode call with a 320ms `setTimeout`:
```js
clearTimeout(debounceRef.current)
debounceRef.current = setTimeout(async () => {
  const results = await geocode(val)
  ...
}, 320)
```

`debounceRef` is a `useRef` (not state) because changing it must not trigger a re-render.

## 8. Express Backend & Middleware

### Setup
`server/index.js` — minimal Express app:
```js
app.use(cors({ origin: process.env.CORS_ORIGIN, credentials: true }))
app.use(express.json())
app.use('/api/auth', authRouter)
app.use('/api/favorites', favoritesRouter)
```

Started with `node --env-file=.env server/index.js` (Node 20+ built-in `.env` loading — no `dotenv` package needed).

### Database connection (`server/db.js`)

```js
import pg from 'pg'
const { Pool } = pg
export const pool = new Pool({ connectionString: process.env.DATABASE_URL })
```

`pg.Pool` manages a pool of persistent TCP connections to PostgreSQL, reusing them across requests. The `connectionString` format is `postgresql://user@host:port/dbname`.

### `requireAuth` middleware

Called as `router.use(requireAuth)` to protect entire route groups, or as an inline argument on individual routes.

```js
const header = req.headers.authorization          // "Bearer <token>"
const token = header.slice(7)                      // strip "Bearer "
const tokenHash = crypto.createHash('sha256').update(token).digest('hex')  // 64-char hex

const { rows } = await pool.query(
  `SELECT u.id, u.email, u.is_admin
   FROM sessions s JOIN users u ON u.id = s.user_id
   WHERE s.token_hash = $1 AND s.expires_at > NOW() AND u.is_active = TRUE`,
  [tokenHash]
)

req.user = rows[0]        // attached to request for downstream handlers
req.tokenHash = tokenHash // needed for logout (delete this specific session)
```

The `$1` is a parameterized query placeholder — `pg` handles SQL injection prevention automatically.

### Parameterized queries everywhere

All SQL in the project uses `pool.query('...WHERE id = $1', [value])` — never string concatenation. This is the standard `pg` defense against SQL injection.

## 9. PostgreSQL Schema Design

### Why UUID primary keys
`gen_random_uuid()` from the `pgcrypto` extension generates v4 UUIDs. Advantages over serial integers: IDs don't reveal record count, can be generated client-side if needed, and are safe to expose in URLs.

### Sessions table design
The token the user holds in `localStorage` is the **raw 32-byte hex token**. The database only stores its SHA-256 hash (`CHAR(64)` — always exactly 64 hex characters). This means:
- Even if the database is dumped, no session can be hijacked from the stored data alone
- The server never needs to look up by user — just hash the presented token and do an O(1) index lookup

### CASCADE deletes
All child tables (`sessions`, `favorites`, `password_reset_tokens`) use `ON DELETE CASCADE` on their `user_id` foreign key. Deleting one row from `users` automatically removes all associated rows — no application-level cleanup needed.

### `updated_at` trigger
```sql
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$;

CREATE TRIGGER users_updated_at
  BEFORE UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

A `BEFORE UPDATE` trigger fires before each row update, overwriting `updated_at` with the current timestamp. This is more reliable than doing it in application code.

### Composite unique constraint
```sql
UNIQUE (user_id, type, item_id)
```
Prevents duplicate favorites at the DB level. The insert uses `ON CONFLICT DO NOTHING`:
```sql
INSERT INTO favorites (user_id, type, item_id, item_name)
VALUES ($1, $2, $3, $4)
ON CONFLICT (user_id, type, item_id) DO NOTHING
```

## 10. Authentication Implementation

### Token generation
```js
const token = crypto.randomBytes(32).toString('hex')  // 64 hex characters = 256 bits of entropy
```

256 bits of entropy makes brute-forcing practically impossible.

### Storage strategy
```
Browser localStorage: raw token ("rtd_token")
Database sessions table: SHA-256(raw token) — CHAR(64) hex
```

The server hashes the incoming token on every request before the DB lookup. This means a database breach doesn't expose valid tokens.

### Timing-attack prevention on login

If you simply return early when no user is found, an attacker can measure response time to determine whether an email exists:
- Email exists, wrong password: slow (bcrypt compare runs)
- Email doesn't exist: fast (no compare)

The fix: always run bcrypt.compare, even against a dummy hash when no user is found:
```js
const dummyHash = '$2b$12$invalidhashpaddingtomatchlength000000000000000000000000'
const hash = rows[0]?.password_hash ?? dummyHash
const match = await bcrypt.compare(password, hash)
```

bcrypt.compare always takes roughly the same time (proportional to the cost factor, 12 rounds ≈ 200–300ms), so both code paths take identical time.

### Password change invalidates other sessions
```sql
DELETE FROM sessions WHERE user_id = $1 AND token_hash != $2
```

The `!=` keeps the current session alive (so the user isn't immediately logged out) but invalidates every other device.

### `apiFetch` helper pattern

Both `AuthContext` and `useFavorites` define a local `apiFetch` wrapper:
```js
async function apiFetch(path, options = {}) {
  const token = localStorage.getItem(TOKEN_KEY)
  const res = await fetch(path, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options.headers,
    },
  })
  if (!res.ok) throw new Error(...)
  return res.json()
}
```

This centralizes token injection so it never has to be done manually per-call.

## 11. State Management Patterns

### React Context for auth

`AuthContext` is the only global context. It holds `user` (null when logged out), `loading` (true during initial token validation), and the auth action functions. Components call `useAuth()` to access these.

The `loading` flag is critical — components that depend on auth state (like `ProtectedRoute` and `useFavorites`) must wait for it before deciding what to render/fetch.

### Polling with `useCallback` + `useEffect`

The `usePoll` internal hook pattern:
```js
const load = useCallback(async () => {
  const result = await fetcher()
  setData(result)
  setLastUpdated(new Date())
}, [fetcher])

useEffect(() => {
  load()
  const id = setInterval(load, interval)
  return () => clearInterval(id)
}, [load, interval])
```

The `useCallback` wrapper on `load` memoizes it so the `useEffect` doesn't re-run (and restart the interval) on every render. The `useEffect` cleanup (`return () => clearInterval(id)`) prevents memory leaks and stale updates after unmount.

### `Promise.all` for parallel fetches

Wherever multiple independent async calls are needed, they run in parallel:
```js
const [positions, delays, stops, directions] = await Promise.all([...])
```

This is faster than `await` chaining (sequential), reducing total wait time to the slowest single call rather than the sum.

### Optimistic UI in `useFavorites`

```js
// Update state immediately, then fire the API call
setFavorites(prev => [...prev, item])
await apiFetch('/api/favorites', { method: 'POST', ... }).catch(() => {})
```

The UI updates instantly on click. The `.catch(() => {})` silently swallows network errors rather than reverting — acceptable for a non-critical feature like favorites.

### Dual-mode favorites (DB vs localStorage)
```js
useEffect(() => {
  if (!user) {
    setFavorites(loadFromStorage())   // read from localStorage
    return
  }
  apiFetch('/api/favorites')          // read from DB
    .then(...)
    .catch(() => setFavorites(loadFromStorage()))  // fallback to localStorage if DB fails
}, [user?.id])
```

The effect re-runs when `user?.id` changes (login/logout). Using `user?.id` rather than `user` prevents unnecessary re-runs if the user object reference changes but the ID is the same.

## 12. Key Algorithms

### Haversine distance

Used in two places: P&R station scoring (`TripPlanner.jsx`) and nearby stop search (`gtfsStatic.js`).

```js
function haversineKm(lat1, lon1, lat2, lon2) {
  const R = 6371  // Earth radius in km
  const dLat = (lat2 - lat1) * Math.PI / 180
  const dLon = (lon2 - lon1) * Math.PI / 180
  const a = Math.sin(dLat/2)**2
    + Math.cos(lat1 * Math.PI/180) * Math.cos(lat2 * Math.PI/180) * Math.sin(dLon/2)**2
  return R * 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1 - a))
}
```

The Haversine formula accounts for Earth's curvature. For distances under ~500km, accuracy is within 0.5%.

### P&R station scoring

```js
const driveDist   = haversineKm(fromLat, fromLon, pr.lat, pr.lon)
const transitDist = haversineKm(pr.lat, pr.lon, toLat, toLon)
const directDist  = haversineKm(fromLat, fromLon, toLat, toLon)
const detourRatio = (driveDist + transitDist) / directDist
```

A station is filtered in if `detourRatio <= 1.4` (route through the station is at most 40% longer than going direct) AND `driveDist < directDist` (the station is not further away than the destination itself). Results are sorted ascending by `detourRatio`.

### Google Polyline decode

```js
export function decodePolyline(encoded) {
  const coords = []
  let index = 0, lat = 0, lng = 0
  while (index < encoded.length) {
    let b, shift = 0, result = 0
    do {
      b = encoded.charCodeAt(index++) - 63  // subtract 63 to get 6-bit value
      result |= (b & 0x1f) << shift         // take lower 5 bits, shift into position
      shift += 5
    } while (b >= 0x20)                      // high bit set means more chunks follow
    lat += (result & 1) ? ~(result >> 1) : (result >> 1)  // zigzag decode
    // same for lng ...
    coords.push([lat / 1e5, lng / 1e5])     // divide by 100000 for decimal degrees
  }
  return coords
}
```

Each coordinate is stored as a delta from the previous (not absolute), which makes the encoding more compact for nearby points. The zigzag decode converts unsigned integers back to signed deltas.

## 13. Leaflet Map Implementation

### Why Leaflet + React-Leaflet

Leaflet is a mature, lightweight mapping library. React-Leaflet provides React component wrappers that register layers via React Context — `MapContainer` creates a Leaflet map and exposes it via context; child components like `Polyline`, `Marker`, `TileLayer` call `useMap()` to access it and add/remove Leaflet layer objects directly.

### `divIcon` for custom markers

Leaflet's default markers are PNG images. Custom markers use `L.divIcon`:
```js
L.divIcon({
  className: '',            // suppress Leaflet's default white box CSS
  html: '<div style="...">Label</div>',
  iconSize: [w, h],         // bounding box in pixels
  iconAnchor: [w/2, h],     // which pixel of the icon sits at the marker's latlng
  popupAnchor: [0, -h],     // where the popup appears relative to the icon
})
```

`iconAnchor` is critical for correct positioning — for a bottom-centered pin, the anchor should be `[width/2, height]`.

### Forcing marker remount on prop change

React-Leaflet's `Marker` calls `marker.setIcon()` when the `icon` prop changes, but this can be unreliable when the icon object changes identity every render. The workaround used for P&R markers:

```jsx
<PRSelectMarker
  key={`${s.id}-${selectedPR?.id === s.id}`}
  ...
/>
```

Changing the `key` forces React to unmount and remount the component, which creates a fresh Leaflet marker with the correct icon from scratch.

### `FitBounds` component pattern

```js
function FitBounds({ points, once = false }) {
  const map = useMap()    // gets the Leaflet map instance from context
  const hasFit = useRef(false)
  useEffect(() => {
    if (!points?.length) return
    if (once && hasFit.current) return
    map.fitBounds(points, { padding: [48, 48], maxZoom: 15 })
    hasFit.current = true
  }, [points, map, once])
  return null
}
```

`useMap()` is a React-Leaflet hook that can only be called inside a `MapContainer` descendant. The component renders nothing (`return null`) — it exists purely to run a side effect on the map instance. The `once` flag prevents re-fitting when the parent re-renders with the same conceptual bounds (used in the P&R map to avoid re-centering on every hover).

The `key` prop on `FitBounds` is used to force a re-fit when the view context changes:
```jsx
<FitBounds key={trip ? 'route' : hasBothCoords ? 'area' : 'stations'} points={fitPoints} />
```

Changing the key remounts `FitBounds`, which resets `hasFit.current` and runs the effect fresh.

### Displaying all trip routes simultaneously

All routes are drawn on the same map — unselected routes first (so they appear behind), selected route last (on top):

```jsx
{/* Unselected — gray, 0.5 opacity, clickable */}
{trips.map((trip, i) => i !== selectedIndex
  ? <TripLegs key={i} trip={trip} selected={false} onSelect={() => onSelectIndex(i)} />
  : null
)}

{/* Selected — full route color, full opacity */}
<TripLegs trip={trips[selectedIndex]} selected onSelect={null} />
```

SVG layers in Leaflet are drawn in DOM order — later elements appear on top. React renders the array in order, so unselected come first in the DOM.
